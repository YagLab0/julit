# Provisioned Origins and producers

JuLit's demonstration covers exactly two Origins — Salar de Peña Blanca, produced by Sales del Altiplano S.A., and Salar del Cóndor, produced by Minera Cóndor S.A. The mine names, the producer names and their reference block are fictional; the salar polygons, plant coordinates and capacity figures stay the geographic reference the demo stands on. The catalogue first shipped real identities (Olaroz / Sales de Jujuy, Cauchari-Olaroz / Minera Exar) with their shareholder and filing references; those are gone so the demo never names a real company or attributes data to it. Before that, the database stored only an identifier and a name, the origin metadata lived hardcoded in the frontend demo data, any visitor could self-register as a producer, and the frontend shipped simulated batches with prices, report digests and event histories that exist nowhere.

The origins table becomes the catalogue: each row carries the short name, `code`, `salar`, the producer's display name, shareholders, processing-plant coordinates, and the reference block — capacity, altitude and water-footprint reference when a value exists, note, source label and URL. Reads stay public, and the Cóndor identifier `condor` is shared by every layer with no translation. Producer companies are bound to exactly one origin at provisioning time, fixed once set ([ADR-0006](./0006-producer-origin-binding-and-company-contracts.md)).

Producer accounts are provisioned, never self-registered: the sign-up route is removed, company onboarding offers only auditor and buyer, and the company registration API rejects the producer type. The two producer companies — one per Origin, named after the origin's producer — come from an idempotent seed with demo-only email and password credentials and no wallet; each producer proves wallet ownership later through the [ADR-0005](./0005-wallet-link-challenges-are-single-use.md) challenge flow.

The Supabase seed runs on `supabase db reset` locally and reaches the linked project through the reviewed `supabase db push --include-seed` runbook. The local smoke (`pnpm smoke`) proves by code that both producers sign in, producer registration is rejected, a fresh auditor registration is accepted, the origins catalogue reads anonymously, and re-running the seed changes nothing.

No simulated batch content ships: the mock fixtures and every batch-only surface are deleted, batch views render an empty state, and the demo map reads Origins from Supabase through the anonymous client. The static data module keeps the geographic reference — salar polygons, export routes and ports — while its on-screen labels and its corridor source line use the demo's fictional identities.

Consequences: adding a producer means extending the seed or provisioning a company and binding its origin — never a self-service signup — and a third origin is a migration plus provisioning. Origin metadata has one source of truth and cannot drift from the database, and nothing in the UI presents unverifiable batch data as real. The producer type remains part of the domain model because batches still require a producer participant.
